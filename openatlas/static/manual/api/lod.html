Linked Open Data

This guide explains how OpenAtlas handles Linked Open Data (LOD) in Version 1, which ontologies are employed, and how research data is structured and serialized.

Why Linked Open Data?

Research data in archaeology, history, and the humanities is inherently heterogeneous and interconnected. OpenAtlas uses Linked Open Data to fulfill the FAIR data principles (Findable, Accessible, Interoperable, Reusable).

By assigning persistent URIs and expressing relationships through formal ontologies, data stored in OpenAtlas can be integrated with international vocabularies (such as Getty AAT or Wikidata) and aggregated across disciplinary boundaries.

OpenAtlas maps database records to internationally recognized domain ontologies:

LOD Profiles in Version 1 (Beta)

OpenAtlas v1 provides two Linked Open Data interfaces, along with W3C SKOS thesaurus exports:

1. Strict Linked Art Profile (/api/1/linked-art/...)

  • Endpoints: * GET /api/1/linked-art/entity/{uuid} (or .../entity/{uuid}.{ext}) * GET /api/1/linked-art/entities/{entity_class}

  • Audience: GLAM institutions (Galleries, Libraries, Archives, Museums), cultural heritage aggregators, and Linked Open Data consumers.

  • Status: Fully supported in v1 Beta (Recommended).

  • Characteristics: Adheres strictly to the Linked Art profile (JSON schemas with additionalProperties: false). Responses strictly conform to Linked Art classes (such as HumanMadeObject, Place, Actor, Activity), providing full entity details, classified types, timespans, citations, and related links.

2. Controlled Vocabularies & SKOS (/api/1/vocabulary/...)

  • Endpoints: * GET /api/1/vocabulary/{id}/skos * GET /api/1/vocabulary/{id}/skos.{ext}

  • Audience: Terminology managers, thesaurus hubs (e.g. SKOSMOS), and SPARQL endpoints.

  • Status: Fully supported in v1 Beta.

  • Characteristics: The root type is structured as a skos:ConceptScheme, with all child nodes linked hierarchically via skos:broader and skos:narrower. Supports standard formats (Turtle, RDF/XML, JSON-LD, N-Triples).

3. OpenAtlas Native CRM Graph (/api/1/entity/...)

  • Endpoints: * GET /api/1/entity/{uuid} (or .../entity/{uuid}.{ext}) * GET /api/1/entities/{entity_class}

  • Status: In Development / Experimental (Alpha Stub).

  • Characteristics: Provides a preliminary, lightweight stub interface returning the entity URI, class type, and label. A comprehensive, deep CIDOC CRM graph serializer with formal property-chain shortcuts is currently under active development and will be introduced in an upcoming release.

  • Recommendation: For production semantic integration in Version 1 Beta, please use the Linked Art endpoints.

Format Selection & Content Negotiation

All Linked Open Data endpoints support HTTP Content Negotiation via the Accept header, as well as explicit URL extensions:

Format

HTTP Header (Accept)

URL Extension

JSON-LD (Default)

application/ld+json

.json

Turtle

text/turtle

.ttl

RDF/XML

application/rdf+xml

.xml

N-Triples

application/n-triples

.nt

Example: Fetching an entity in Turtle format using content negotiation:

curl -H "Accept: text/turtle" https://demo.openatlas.eu/api/1/linked-art/entity/913322f4-a3cf-2e90-bfd1-cecc8e523b56

Or by appending .ttl directly to the URL:

curl https://demo.openatlas.eu/api/1/linked-art/entity/913322f4-a3cf-2e90-bfd1-cecc8e523b56.ttl
